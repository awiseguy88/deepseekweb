# WiseAI platform roadmap

Status legend: `[x]` shipped and verified in the hosted deployment; `[ ]` not shipped; each open item names its acceptance check. This file is the single owner of the commercial-readiness backlog; update it in the same pull request as each change.

Scope note: the admin command-center mockups in the audit are **design references only** — no mock metrics are served to operators. Operators see real database values.

## Shipped

- [x] **Removed the destructive "Remove test data" admin action.** `POST /admin/api/cleanup` (which deleted every non-operator tenant) and its UI button are gone. Test fixtures are now identified only by the explicit `@wiseai.example` domain and are deleted by a targeted boot job; that job never touches a tenant containing any other address.
- [x] **Session cookies are Secure from deployment configuration, not the proxy connection.** `WISEAI_SECURE_COOKIES=1|0` overrides; otherwise an HTTPS public URL enables Secure.
- [x] **Commercial entitlement enforcement in session admission.** Session lookup and issuance require an entitled tenant: `active`/`trialing`, or `past_due` with an explicit access date inside `WISEAI_ACCESS_GRACE_DAYS` (default `0`). `canceled`/`disabled`/expired tenants are refused.
- [x] **Same-origin protection for cookie-authenticated mutations.** Admin API, support intake, account API, login, and sign-out reject cross-site `Origin`/`Referer` authorities.
- [x] **Dead login sessions purge.** Revoked session rows are deleted on boot and by an admin button (`POST /admin/api/sessions/purge-revoked`), replacing unbounded audit-free revocation residue.
- [x] **One live login session per account**, so the "active sessions" metric tracks accounts rather than accumulated sign-ins.
- [x] **Tenant isolation for sessions and workspaces** through the remote-access policy plus first-wins ownership claims (visibility isolation).
- [x] **Hosted domain and branding fixes.** `RAILWAY_PUBLIC_DOMAIN` is trusted and advertised, the whale marks were replaced with the W mark, and session resume recovers a vanished container workspace into `/data/workspace`.
- [x] **Hosted capacity controls.** Concurrent subagents raised to 32 (override `WISEAI_MAX_ACTIVE_SUBAGENTS`); tenant customer delete and session revoke/purge remain platform/tenant-admin scoped.

## Critical — before accepting paying customers

- [ ] **C1. Explicit tenant capability allowlist.** In progress: tenant peers now receive only an explicit Remote/event allowlist (`account/*`, `session/*`, `workspace/*`, settings, jobs, terminal, directory picker, skills, file references, plugin inventory, forwarded session events). Unmatched endpoints are denied, including endpoints a newly mounted plugin contributes, and each boot warns with the denied list; `WISEAI_TENANT_ACTIONS` overrides the list. Remaining: named per-resource capability roles (global/session/workspace) and tool-level capabilities (files, terminal, browser, plugins, computer control, agent creation, scheduled jobs) enforced in execution. Acceptance: a fixture endpoint not on the allowlist is denied through the executor; capability changes are configuration; tests cover each role/resource combination.
- [ ] **C2. Filesystem and execution isolation.** In progress (application-level scoping shipped): every tenant gets a root under `/data/workspaces/tenants/<tenantId>` created mode `700`; the directory picker, workspace creation, and session creation confine tenant callers to that root (traversal and symlink escapes rejected, native picker disabled for tenants), and tenant default workspaces resolve below the volume. Remaining (requires architecture): OS-level read/write confinement for tools, shell, browser, computer-use, and PTC inside a tenant session — a single shared process cannot enforce this, so the next step is per-tenant worker processes wrapped with bubblewrap (or one container per customer), plus disk-quota enforcement and off-volume backups. Acceptance: two-tenant end-to-end test proves tenant A cannot read tenant B files through any tool, shell, browser, or PTC path; sandbox mode and path policy are explicit per deployment.
- [ ] **C3. Safe destructive admin operations.** In progress: customer deletion is now recoverable (soft delete) behind an impact preview, typed-name confirmation, and administrator reauthentication, and emits an audit event; every admin mutation still needs audit coverage and an approval/restore window. Acceptance: preview lists exact affected rows; no mutation executes without fresh reauth plus confirmation; every step emits an audit event; deleted tenants are restorable from the admin UI.
- [ ] **C4. Transactional Stripe webhook inbox.** In progress: verified events are claimed in `wiseai_billing_events` before any tenant mutation; duplicates are acknowledged without reapplying; failures return 500 and can be reclaimed on Stripe's retry; each event records Stripe's `created` time and resolved tenant, and an older delivery is skipped when a newer event for that tenant was already processed. Remaining: dead-letter review UI and reconciliation directly against Stripe. Acceptance: replaying old/duplicate/delayed events cannot regress subscription state; tests cover ordering and forced failures.

## High — required before scaling

- [ ] **H1. Transactional ownership claims.** In progress: ownership claims now persist and await the store before publishing to the in-memory policy, and a failed write rejects instead of granting temporary access (`claimSession`/`claimWorkspace` return promises; session and workspace creation await them; tests cover the rejection). Remaining: roll back a created Session/Workspace when its claim write fails, so no unowned resource survives the failure. Acceptance: injected database failure fails the create path deterministically, removes the created resource, and a restart restores exactly the persisted owners.
- [ ] **H2. Immutable audit history.** In progress: `wiseai_audit_events` is append-only with `GET /admin/api/audit`; every successful admin mutation appends one record (actor, action, target, path), the Stripe webhook records billing events, the customer soft-delete records its detailed event, and the admin console has a Security & audit tab with the event table. Remaining: permission/approval/agent-approval audit coverage and an export/retention policy; records cannot be updated or deleted through the API.
- [ ] **H3. Authentication abuse hardening.** In progress: sign-in failures are throttled per account + client (8 failures / 15 min, configurable, 429 with `Retry-After`, bounded key set); session cookies are Secure from deployment config; CSRF origin checks cover auth/admin/account/support mutations. Remaining: signup throttling, verified email change and password recovery, distributed/shared limits across instances. Acceptance: rate limits are configurable and tested; recovery and email verification require proof of mailbox control.
- [ ] **H4. Immediate suspension revocation.** In progress: disabling a tenant (status canceled/disabled or account disabled) now revokes every live login session for that tenant/user and emits an audit record, so existing cookies stop working. Remaining: stop running agents, subagents, scheduled jobs, and worker leases on suspension. Acceptance: a suspension test observes running work stopped and cannot be resumed with an existing cookie.
- [ ] **H5. Entitlement and metering model.** In progress: migration 007 creates `wiseai_entitlements` (plan capabilities, concurrency, compute allowance, allowed tools/models), `agent_runs`, `usage_events`, `approval_requests`, and `worker_leases`; usage facts can be appended idempotently and aggregated per tenant/kind/provider/model. Remaining: enforcement before agent execution and for long-running jobs, and wiring runtime producers into `usage_events`/`agent_runs`. Acceptance: exceeding a concurrency, budget, or tool entitlement is refused with a structured error; usage is idempotent per run.
- [ ] **H6. Operations command center.** In progress: the admin console has real Overview counts, Customers, Users, Support, Sessions, Sales, Security & audit, **Usage & costs** (stored usage aggregates), and a Customer 360 activity panel backed by stored data. Remaining: Agent Fleet, Runs & Jobs, Billing, Infrastructure modules; runtime-enforced resource allocation; no mock numbers anywhere. Acceptance: every widget reads a real table or event stream; allocation changes are audited and observed by the runtime.
- [ ] **H7. Metering/control-plane schema and event ingestion.** In progress: migration 007 ships the metering/control tables, `recordUsageEvent` (idempotent) and `usageSummary` store methods, and `GET /admin/api/usage` returning real aggregates; the admin Usage & costs tab renders them. Remaining: a producer that records provider tokens, compute time, cost, and run trees from execution, plus worker-lease heartbeats and expired-lease recovery. Acceptance: a multi-step run with subagents produces one traceable run tree with usage rows and recoverable leases.
- [ ] **H8. Customer workspace and landing page UX.** Navigation (Home, Tasks, Agents, Projects, Automations, Integrations, Usage, Settings), three-panel task view with live activity/permissions/cost, visual patch-preview-approve-rollback editing, real sandboxed landing demo or recorded genuine execution, onboarding and early-access funnel, evidence-based capability claims, and branding audit (for example `apps/web/index.html` mobile title). Acceptance: usability review and browser smoke tests for each route; landing demo either executes sandboxed work or is labeled as scripted.
- [ ] **H9. Real billing portal.** Replace `/account` → `/admin` "View invoices" with a Stripe customer portal session; keep support separate. Acceptance: customer can open the portal, see invoices/payment methods, and return to the account page.
- [ ] **H10. Pricing, margin, and product analytics.** Subscription tiers for features/concurrency plus compute allowances with explicit overage consent and hard budget stops; track MRR, expansion/churn/refunds, true cost per run, activation, retention, reliability, and gross profit per active customer. Acceptance: one dashboard query answers "gross profit per active customer" and "first-session meaningful task completion" from stored events.
- [ ] **H11. Startup readiness without process exit.** A `process.exit(1)` fail-fast attempt crashed the hosted service on boot and was rolled back. Serve a readiness endpoint that stays 503 until migrations and the tenant authorization policy are initialized, and let Railway health checks gate traffic. Acceptance: an injected migration failure produces 503 readiness and no successful logins; normal boot reaches 200.

## Delivery phases

1. **P0 (blocks revenue):** C1, C2, C3, C4, H1, H2.
2. **P1 (scaling and trust):** H3, H4, H5, H7, H9.
3. **P2 (operator and customer experience):** H6, H8, H10.

Each phase ends with: security review, two-tenant end-to-end isolation test, audit coverage check, and an operator runbook update.
